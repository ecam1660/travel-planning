## What this is

A personal travel-prep site for tracking species (birds + non-birds) expected on a
Malaysia & Singapore trip, studying bird ID before the trip, and marking where things
were seen on a map. Static HTML/JS/CSS, no build step, no framework. Data lives in two
CSV files that each page loads client-side via XHR. Pushed to GitHub, served via GitHub
Pages.

Live pages:
- `index.html` — bird species tiles (targets + observed), filterable
- `nonbirds.html` — non-bird species tiles (mammals, reptiles, butterflies, flowers, etc.)
- `flashcards.html` — bird ID flashcard game using photos in `photos/`
- `map.html` — interactive Singapore-centered Leaflet map plotting sightings/locations from both CSVs

## Data model notes

- `location.csv` header: `Malaysia & Singapore, New, Order, Family, Full Location, Date, ID, Location, Rarity, Fam, Freq, Features, Where, Key, Category 1, Category 2, Category 3, Photo, SGroup, Merlin`
  - `New` = "Yes" means not yet observed (a target); convention is `New == "no" → observed`.
  - `TITLE` throughout = the CSV's first header cell (species name column), trimmed — this is the key used to build localStorage keys (see below).
- `nonbirds.csv` categories currently in use: Lizards, Mammals, Butterflies, Damselflies, Dragonflies, Frogs & Toads, Snakes, Flowers.
- CSV parsing uses a shared `splitRow`/`parseCSV` pattern (handles quoted commas) with a case-insensitive `col()` header lookup — this logic is **duplicated across pages**, so keep them in sync if the schema changes.
- Photo filenames are generated by `photoSlug(name)`: lowercase, strip curly quotes/apostrophes, non-alphanumeric → `_`, trim leading/trailing `_`. Variants beyond the first photo are `_2.jpg`, `_3.jpg`, etc.
- No database, no backend — editing the CSVs directly (or via a script) is how data changes.

## localStorage keys (must match exactly across pages for shared state to work)

- Bird observed overrides: `'travel_observed_' + TITLE.replace(/\s/g,'_')`
- Nonbird observed overrides: `'nonbirds_observed_' + TITLE` (verbatim, no replace)
- Starred species (flashcards): `'fc_starred_' + TITLE.replace(/\s/g,'_')`
- Map pins: `'travel_map_pins_' + BIRD_TITLE`
- Tile-back editable Features/Where (index.html): `'travel_text_' + TITLE.replace(/\s/g,'_')` → `{ speciesName: { features, where } }`

Get these exactly right when touching any page that reads/writes shared state — a mismatched key silently breaks cross-page sync instead of erroring.

## Design system

- Palette: ochre/tan/cream; Georgia serif headings; shared CSS custom properties across pages (`--ink`, `--header-bg: #4a6e68`, etc.) — reuse these tokens rather than inventing new colors.
- Category tiles use per-category `--c1/--c2/--c3/--cd` color sets (see `nonbirds.html`).
- Category pills are solid-colored normally; `Widespread`, `Infrequent`, and `Infreq` get a subtle transparent/bordered treatment instead (1px border in the tile's dark text color, opacity .4).
- `.pt-cat-pill` has a fixed height with flex-centered content so text pills and icon pills always line up.
- Merlin sound-ID: small custom SVG speaker icon (`ICON_SPEAKER` — polygon speaker cone + one sound-wave arc, not an emoji), shown as a pill next to the Category pills when `Merlin = Yes`. There's also a nav toggle chip (`#st-merlin`, next to the no-photo camera chip) that filters the grid to Merlin-only species.
- Tile backs (index.html) have directly-editable Features/Where textareas (`spellcheck="false"`), fixed height (2 lines Features, 1 line Where), no scrollbar ever, magnifying-glass/pin icons always shown.

## flashcards.html specifics

- Modes: Easy (5-option multiple choice, wrong answers drawn from the same SGroup), Medium (type + autocomplete), Hard (type only, no autocomplete).
- Result panel always shows the species name — no "Species:" prefix when correct, "Answer: " prefix when wrong.
- Family row renders as plain left-aligned text `"Family: X"`, same size/treatment as the Features/Where icon rows — not a two-column label/value grid.
- `PHOTO_VARIANTS` object maps species name → photo count, used by `pickPhotoSlug()` to randomly show `photos/{slug}_2.jpg`, `_3.jpg`, etc. Auto-regenerated by `add_photos.py` — don't hand-edit it unless syncing in a fresh script run's output.

## map.html specifics

- Leaflet 1.9.4 + OpenStreetMap tiles, centered on Singapore.
- Pin data model: `{id, lat, lng, title, desc, species:[{name, notes}]}` — single ordered list, drag-to-reorder via a `⋮⋮` handle.
- `migratePin()` upgrades any old-format (many/some/few columns) pin on load without data loss.
- Leaflet quirk: `disableClickPropagation` blocks `mousedown`/`touchstart`/`dblclick`/`contextmenu` from bubbling out of popups, but **not** `click` — use click delegation (not mousedown) for anything inside a popup.

## Workflow

**Adding photos:** drop files in `photo_inbox/` → run `python3 add_photos.py` locally (safe to re-run anytime, even with an empty inbox — it always rescans everything; prints a git add/commit/push reminder at the end) → commit `photos/` + `flashcards.html`.

**Refreshing bird data:** `push_data_travel.sh`, run by the user locally, pulls the newest condensed CSV export from `~/Downloads` into `location.csv` and pushes it.

**Publishing from a Claude session:** this repo's `origin` remote already has push credentials embedded (a GitHub PAT), so no extra auth setup is needed in principle. In practice, the sandbox shell can read the connected local folder but can't reliably *delete* files in it (git's lock-file create-then-remove pattern fails there) — so the working method is: copy the repo to the sandbox's own local disk (e.g. `/tmp`), commit and push from there, then rely on the host-side Write/Edit tools (not bash) to make sure the actual file content lands in the connected folder. The user's local Desktop copy of `.git` will trail by whatever was pushed until they next `git pull` there themselves — the working files match already, so that pull is always a clean fast-forward.

**Typical loop:** update CSV/HTML → `git add -A && git commit -m "..."` → `git push`.

Security note: the PAT is sitting in plaintext in `.git/config` — fine for a personal project, but don't share this repo's git config, and rotate the token if that ever changes.

## Known gotchas

- Files (especially `flashcards.html`) can end up locked (`-r--------`), likely from iCloud/Finder sync — fix with `chmod u+w <file>` before running scripts that write to it.
- Re-uploading a file to chat under a filename already used earlier in the conversation can silently serve a stale cached copy instead of the new content. If a re-upload looks suspiciously identical (same size) to an old version, don't trust it — ask for the relevant text/code pasted directly instead.
- GitHub PAT (classic, `repo` scope) auth: macOS's `osxkeychain` credential helper can cache a stale/invalid token without prompting for a new one. Fix via `git credential-osxkeychain erase` (`printf "protocol=https\nhost=github.com\n" | git credential-osxkeychain erase`) or by embedding the token directly in the remote URL. **Never let a real token get pasted into chat** — flag it as compromised immediately if it happens.
- Claude's sandbox shell can read the connected local folder but can't always write (specifically: can't delete/replace lock files) directly to it — the host-side Read/Write/Edit tools are the reliable path for saving file changes; git operations need the `/tmp`-copy workaround described above.

## Verification pattern

No headless browser is available in this environment, so after every JS edit: extract the `<script>` block and run `node --check` on it to catch syntax errors. For trickier logic (localStorage persistence, pin migration, drag-reorder), a quick jsdom-based test harness has been used to simulate behavior before trusting a fix.
